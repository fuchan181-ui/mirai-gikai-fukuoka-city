# TypeSafe（System One / Jev）導入検証計画

## 背景と目的

本サービスは AI インタビューで集めた市民意見を、モデレーション・情報充実度評価・
トピック分析などの判定に通している。いずれも「LLM にプロンプトを投げて JSON を
受け取り、コードで解釈する」形で、判定の粒度が粗く、閾値の調整に再推論が必要で、
判定理由が確率として残らないという課題がある。

TypeSafe の System One モデル（Jev）は、自然言語を **型付きの判断と確率** に変換する。
テキストを生成せず、`noul`（yes/no 確率）・`score`（順序尺度）・`choice`（選択）を
返すため、判定を「プログラミングプリミティブ」としてコードで合成できる。

目的は置き換えそのものではなく、**置き換える価値があるかを数字で決める**こと。
特に日本語の判定性能が未検証であり、ここを最初に測る。

## 現状の LLM 判定箇所（棚卸し）

| 判定 | 実装場所 | 現状の形 | TypeSafe 化の狙い |
| :-- | :-- | :-- | :-- |
| モデレーション | `packages/shared/src/moderation/` | 13 カテゴリ → 0-100 → 30/70 閾値 | カテゴリ別確率 + リスク別の非対称閾値 |
| 情報充実度 | `packages/shared/src/content-richness/` | 4 次元 + total を一括採点 | total をコードで合成し、重み変更に再推論を不要にする |
| 意見タグ | `packages/shared/src/interview-report/opinion-tags-schema.ts` | 7 値の列挙を生成 | 値ごとの `noul` に分解 |
| トピック抽出/統合/割当/採用判定 | `packages/topic-analysis-core/src/services/` | TSV 手書きパース（壊れやすい）、番号配列 + 防御的正規化 | `choice` / 階層分類 |
| 議案タグ・サムネイル題材 | `packages/bill-explainer/src/utils/` | 列挙の生成 | `choice` |
| インタビューシミュレーション | `admin/src/features/interview-simulation/` | 生成 | 変更なし（生成タスクのため対象外） |

## 提案（優先順位順）

1. **モデレーション → 13 カテゴリの `noul` + リスク別非対称閾値**（最優先）
   - 0-100 の単一スコアではカテゴリごとの重みを表現できない。カテゴリ別確率なら
     「個人情報は厳しく、不謹慎は緩く」をコード側のデータとして持てる
   - 閾値調整に再推論が不要
2. **情報充実度 → 4 次元の `score` + total はコード合成**（最優先）
   - 重みを変えても再推論が不要。次元別の確信度も取れる
3. 意見タグ `reasoning_types` → 7 値の `noul`（高）
4. `judge-new-topics` → 候補ごとの `noul` fan-out（高）
5. `assign-opinions` → `choice` / 階層分類（中）
6. 議案タグ・サムネイル題材 → `choice`（中）

### 新機能の候補

- 賛否理由の分類（賛成理由 / 反対理由 / 条件付き賛成を `choice` で）
- 対立論点の可視化（意見間の論点一致を `noul` で総当たり）
- 一般質問 × 議案のマッチング
- 意見トリアージ（対応優先度を `score` で）
- AI チャット前段のガード（議案と無関係な質問を `noul` で弾く）
- 解説 QA（生成した解説が原文に忠実かを `noul` で検証）

## Phase 0: 検証基盤（本 PR の範囲）

`packages/ai-judge-eval/` を追加した。本番コードからは参照されない開発専用パッケージ。

- OpenAI 版（本番と同一経路）と TypeSafe 版を **同じ入力・同じ期待ラベル**で実行し、
  精度・レイテンシ・コストを並べて markdown レポートに出す
- 期待ラベルは既存 LLM の出力からではなく、既存プロンプトの基準を読んで人手で付与
- モデレーションは見逃し・過検知・重大な見逃し（ng→ok）を分けて集計
- 情報充実度はレベル一致率・±1 レベル以内・MAE・バイアスで集計
- `--dry-run` で API キーなしに配線を検証できる
- レポート末尾に判定器 × 対象ごとのトークン数・推定コストを出す
- `--out` 指定時は markdown に加えて JSON も書き出し、カテゴリ別確率・次元別スコアを
  保存する（閾値や重みを変えたときの再計算用。再推論は不要）
- `--repeat` のぶれはケース単位で測る。モデレーションはラベルの変化、
  情報充実度はケースごとの標準偏差

判定基準（すべて満たせば Phase 1 へ）:

| 観点 | 基準 |
| :-- | :-- |
| 重大な見逃し | `ng → ok` が 0 件 |
| 過検知 | ok ケースの `ok → ng` が 0 件 |
| 充実度 | ±1 レベル以内が 100% |
| レイテンシ | 中央値が OpenAI 版の 1/3 以下 |
| コスト | 1 ケースあたりの費用が OpenAI 版以下 |

詳細は `packages/ai-judge-eval/README.md` を参照。

## Phase 0 の結果（2026-09-18）

`jev-1.13.0` / `openai/gpt-5.6-luna`、`--repeat=3`、モデレーション 21 件・
情報充実度 5 件。モデレーションの期待ラベルは境界事例を対で付け直し
（著作権処理を問いただす意見は `ok` / 他人の文章をまとまった量そのまま貼るのは `ng`、
過去の役職への言及は `ok` / 公的な立場で発言していると主張するのは `warning`、
氏名つきの個人情報も住所のみの個人情報も `ng`）、`criteria` の例文も
評価ケース本文から独立させた（例文に答えを書くと一致率が過大評価になるため）
うえで測った。

| 観点 | 基準 | 結果 | 判定 |
| :-- | :-- | :-- | :-- |
| 重大な見逃し | `ng → ok` が 0 件 | 0 件 | 達成 |
| 過検知 | ok ケースの `ok → ng` が 0 件 | 0 件 | 達成 |
| 充実度 | ±1 レベル以内が 100% | 100% (5/5) | 達成 |
| レイテンシ | 中央値が OpenAI 版の 1/3 以下 | 249ms（OpenAI 2298ms の約 1/9） | 達成 |
| コスト | 1 ケースあたりの費用が OpenAI 版以下 | **未判定**（単価未登録） | 保留 |

一致率はモデレーション 100.0% (21/21)・情報充実度のレベル完全一致 60.0% (3/5)。
OpenAI 版はそれぞれ 76.2% (16/21)・80.0% (4/5) で、過検知（ok→ng）と
判定のぶれ（2/21 ケース）が出ている。TypeSafe 版は過検知 0 件・ぶれ 0/21 ケース。

### 構造化（公式ドキュメント準拠）でやったこと

公式ドキュメントの [Advanced: structure](https://docs.typesafe.ai/primitives/advanced)
と [How to build with System One](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)
に合わせて、プロンプトを次の形にした。

- Noul（モデレーション）: `instructions: { question, focus }`、
  `criteria: { true: { what, examples }, false: { what, examples } }`
- Score（情報充実度）: `instructions: { question, note }`、
  `criteria: [{ summary, signals }]`
- 共通の判定ポリシーは state に 1 か所だけ置く（`MODERATION_EVALUATION_POLICY`）
- state の path はバッククォートで参照（`` `conversation` `` など）
- 1 問 1 判定に分解（13 カテゴリを別々の `noul` にする）

効果は一致率だけでなく確率の鋭さに出た。構造化前は閾値をまたいでいた
`warning-impersonation` が 0.35〜0.40 で不安定だったのが、構造化後は 0.96〜0.97 で
安定した。判定のぶれも 3 回反復で 0/19 ケースになった。

### 残った論点

- **境界は `criteria` の false 側の書き方で決まる。** 著作権の「短い引用や権利処理を
  問う意見は該当しない」、なりすましの「過去の役職への言及は該当しない」を書いた
  ことで、紛らわしい境界事例 5 件を両方向とも正しく捌いた
- **確信度が低いケースだけが期待ラベルとずれる。** 情報充実度でずれた 2 件は
  確信度 0.62 / 0.71、一致した 3 件は 0.97〜1.00。確信度を使ったトリアージ
  （低確信度だけ人手で確認、低確信度だけ別の判定器に回す）が組める
- **情報充実度のぶれが 0.0 点**（OpenAI 版は 1.4 点）。同じ入力に対して
  3 回とも同じレベルを返しており、閾値運用が読みやすい
- **TypeSafe の単価が `model-pricing.ts` に無い**ため、コスト基準だけ未判定。
  Phase 1 の前に課金体系を確認する
- **ng 閾値には下限がある。** 現在 0.35。0.30 まで下げると政策への強い反対
  （`clean-strong-opposition`）を `ng` にするため、見逃し 1 件に合わせて下げる
  調整幅は残っていない
- **情報充実度の期待ラベルは 5 件**しかなく、レベルの 1 段差は基準の文言上
  どちらとも読める。ラベルを出力に寄せず、ケースを増やして境界の分布を見る
- **本番の既定モデルは `gpt-5.2`**（`DEFAULT_MODERATION_MODEL` /
  `DEFAULT_CONTENT_RICHNESS_MODEL`）。方針として `gpt-5.6-luna` だけを使うなら、
  本番定数の見直しを別 PR で行う

## 制約とリスク

- **日本語性能が未検証** — これが Phase 0 の主たる測定対象。落ちた場合、提案は
  英語圏向けの話であり、この種の判定には使えないことになる
- **コスト管理に載らない** — `packages/shared/src/ai/model-pricing.ts` は
  OpenAI 互換のトークン単価を前提にしており、TypeSafe の課金体系は別。
  `system-cost-guard.ts` の日次/月次上限に統合するには Phase 1 で別途設計が要る。
  評価ハーネスはトークン数と推定コストを記録するが、TypeSafe 分は「単価未登録」
  として表示されるため、コスト比較は手動で突き合わせる
- **プロバイダ分離** — `resolveOpenAiModel` は OpenAI 以外を例外にする設計。
  TypeSafe を本番経路に入れるなら、判定器の抽象化とプロバイダ選択が必要
- **API キー** — `TYPESAFE_API_KEY` の追加が必要（`.env.example` に追記済み）
- **SDK のブラウザ禁止** — API キー露出を避けるため、SDK はブラウザ実行時に例外を
  投げる。サーバー側専用
