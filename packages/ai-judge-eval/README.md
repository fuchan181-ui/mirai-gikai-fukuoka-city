# @mirai-gikai/ai-judge-eval

LLM に任せている判定を、TypeSafe（Jev）の構造化された判定に置き換えられるかを
**同じ入力・同じ期待ラベルで測る**ための検証ハーネス。本番コードからは参照されない
開発専用パッケージ。

Phase 0 の目的は「置き換える」ことではなく、**置き換える価値があるかを数字で決める**
こと。判定精度・レイテンシ・コストの3点で比較する。

## 何を比較しているか

| タスク | OpenAI 版（基準） | TypeSafe 版（提案） |
| :-- | :-- | :-- |
| モデレーション | 13 カテゴリを 1 プロンプトで読ませ、0-100 スコア → 30/70 閾値で ok/warning/ng | 13 カテゴリをカテゴリごとの `noul`（yes/no 確率）に分解し、確率をコード側でステータスに合成 |
| 情報充実度 | 4 次元 + `total` をまとめて 0-100 で採点 | 4 次元を `score` で採点し、`total` は重み付き平均でコード側合成 |

OpenAI 版は**本番と同一の経路**（同じプロンプト・スキーマ・モデル・閾値）を通す。
比較の基準側なので、こちらの実装は変更しないこと。

ただし本番は Vercel AI Gateway 経由、このハーネスは OpenAI へ直接リクエストする。
判定結果は同じ条件で比較できるが、**絶対レイテンシ・実費は本番と一致しない**
（相対比較の指標として読むこと）。

TypeSafe 版の `severity` はカテゴリ単位で決まるため、同じカテゴリの中の強弱
（例: 実名を出した政策批判と、実名での人格攻撃）はカテゴリではなく
`noul` の `criteria.true` / `criteria.false` の記述で切り分ける。

## 評価セットの設計方針

- **期待ラベルは人手で付ける**。既存 LLM の出力を正解にすると、既存実装の誤りを
  そのまま焼き付けてしまい、改善余地が見えなくなる。
- **境界事例を意図的に入れる**。`clean-strong-opposition`（強い反対意見）や
  `warning-strong-criticism-with-naming`（実名入りの強い批判）は、モデレーションで
  最も誤りやすい「政策批判と誹謗中傷の境目」を突くために置いている。
- **ローカルの本番データは使わない**。開発 DB のレポートはプレースホルダ値で、
  実データを使うとプライバシー面の懸念もあるため、ケースはすべて合成。

## 閾値と severity の決め方

`TYPESAFE_MODERATION_POLICY` の閾値（ng 0.35 / warning 0.5）と、
`MODERATION_CATEGORIES` の `severity` は**既存プロンプトの記述から導出**している。

- 既存プロンプト: `70-100（ng）= 公開に適さない内容`、`30-69（warning）= 注意が必要だが
  意見としての価値はある`、`0-29（ok）= 問題なし`
- したがって「該当したら公開に適さない」カテゴリを `ng`、「該当しても意見としての
  価値は残る」カテゴリ（不謹慎・なりすまし）を `warning` とした
- 閾値は見逃しのコストが高いので ng 側を低く取っている（非対称閾値）

これは**仮の policy** であり、Phase 0 の結果を見て調整する前提。調整する場合は
`combineCategoryProbabilities` の閾値を注入して再計算できる（再推論は不要）。

## 実行方法

```bash
# 配線だけ確認する（API キー不要。期待ラベルをそのまま返すので全一致になる）
pnpm --filter @mirai-gikai/ai-judge-eval eval -- --dry-run

# モデレーションだけ、両判定器で 3 回ずつ
pnpm --filter @mirai-gikai/ai-judge-eval eval -- --only=moderation --repeat=3 \
  --out=docs/typesafe-phase0-$(date +%Y%m%d).md

# TypeSafe 側だけ
pnpm --filter @mirai-gikai/ai-judge-eval eval -- --judge=typesafe
```

必要な環境変数:

- `OPENAI_API_KEY` — `--judge=openai` または `all` のとき
- `TYPESAFE_API_KEY` — `--judge=typesafe` または `all` のとき

オプション一覧は `eval -- --help` を参照。

`--out` の相対パスは**リポジトリルート基準**で解決する（`pnpm --filter` は cwd を
パッケージ配下に変えるため、`docs/...` と書いてもリポジトリ直下の `docs/` に出る）。

`--out=<path>.md` を指定すると、同じディレクトリに `<path>.json` も書き出す。
JSON には**判定器の完全な出力**（カテゴリ別確率・次元別スコア・usage・レイテンシ）が
入るので、閾値や重みを変えたときに再推論せず再計算できる。

## 出力の読み方

### モデレーション

- **見逃し** — 期待より軽い判定になった件数。不適切な意見を公開してしまう誤り
- **過検知** — 期待より重い判定になった件数。適切な意見を非公開にしてしまう誤り
- **重大な見逃し（ng→ok）** — 公開事故に直結するので最重要。ここが 0 でなければ不採用
- **混同行列** — どのラベル間で取り違えているかを見る
- `--repeat=2` 以上を指定すると、同じ入力で判定が変わったケース（ラベルのぶれ）を出す

一致率だけを見ると「過検知で落とす癖」と「見逃す癖」を区別できないため、
深刻度の大小で分けて数えている。

### 実行コスト

レポート末尾の「実行コスト」表に、判定器 × 対象ごとのトークン数と推定コストを出す。
単価は `packages/shared/src/ai/model-pricing.ts` を使うため、**TypeSafe の単価が
未登録だと「不明」になる**（0 ではなく不明として扱う）。判定基準のコスト比較を
自動で判定するには、Phase 1 で TypeSafe の課金体系を同ファイルに足す必要がある。

### 情報充実度

- **レベル完全一致 / ±1 レベル以内** — 5 段階なので ±1 は実用上の許容幅
- **平均絶対誤差（MAE）** — 0-100 スケールでの平均的なずれ。ただし期待値は
  レベル帯の中点（レベル 4 = 90 点）、TypeSafe の判定はレベルを 0-100 に線形換算
  した値なので、**レベルが完全一致していても ±10 点の目盛り差が出る**。
  判定器をまたぐ比較には次のレベル単位の誤差を使う
- **レベル単位の誤差** — レベル差の平均絶対値とバイアス。目盛りに依存しないので
  OpenAI 版と TypeSafe 版を直接比較できる
- **バイアス** — 正なら過大評価、負なら過小評価の癖
- `--repeat=2` 以上を指定すると、**ケースごとの**標準偏差の平均・最大も出す。
  全ケースをまとめて標準偏差を取ると、モデルのぶれではなくケース間の内容差
  （レベル 0 と 4 の差）を測ってしまうため、ケース単位で区切っている

## Phase 0 の判定基準

以下をすべて満たしたら Phase 1（プロバイダ分離と本番経路への組み込み）に進む。

| 観点 | 基準 |
| :-- | :-- |
| 重大な見逃し | `ng → ok` が **0 件**（OpenAI 版と同等以上） |
| 過検知 | ok ケースの `ok → ng` が **0 件** |
| 充実度 | ±1 レベル以内が **100%** |
| レイテンシ | 中央値が OpenAI 版の **1/3 以下** |
| コスト | 1 ケースあたりの費用が OpenAI 版以下 |

満たさない場合は、閾値・severity・カテゴリ分割の粒度を見直して再測定する。
**カテゴリごとの確率が取れるので、閾値の調整に再推論は要らない**のがこの分解の利点。

## この評価セットの限界

- モデレーション 18 件（本番プロンプトの 13 カテゴリをすべて 1 件以上含む）・
  充実度 5 件。**合否を分けるゲートとしては機能するが、
  精度の推定値としては標本が小さい**。採用後は実データでの継続監視が必要。
- ケースは沼津市議会の文脈で書いている。他自治体に展開する際は言い回しの
  再確認が必要。
- TypeSafe の単価が `model-pricing.ts` に未登録のため、コスト比較は実行後に
  手動で突き合わせる必要がある（トークン数は記録される）。
- 日本語の判定性能は未検証。ここを測るのが Phase 0 の主目的。

## SDK のバージョンについて

`@typesafe-ai/sdk` は `0.5.7` に固定している。リポジトリの
`minimumReleaseAge: 4320`（3日）を満たす最新版がこれだったため。
`0.6.0` とは `score` の criteria の最小要素数（1 件 → 2 件）が変わるだけで、
本パッケージが使う API（`noul` / `score` / `choice` / `systemOne`）は同一。
quarantine 期間が明けたら `0.6.0` へ上げてよい。

なお TypeSafe SDK は API キーが露出するためブラウザ実行を禁止している。
このパッケージは CLI（サーバー側）専用。
